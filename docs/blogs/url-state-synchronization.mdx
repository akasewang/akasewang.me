Searchable lists often begin with a few local state variables:

```tsx title="local-state-example.tsx"
import { useState } from 'react'

export function useLocalListState() {
  const [searchQuery, setSearchQuery] = useState('')
  const [category, setCategory] = useState('all')
  const [sortBy, setSortBy] = useState('date-desc')

  return { searchQuery, category, sortBy, setSearchQuery, setCategory, setSortBy }
}
```

That is enough to filter the current render, but the state disappears at the browser boundary. A copied link opens the default list. Refreshing clears the selection. Returning from a detail page may lose the exact view the reader left.

Search, category and sorting state belong in the query string when they describe the page being viewed:

```text
/projects?q=interactive&category=web&sort=views-desc
```

The URL then becomes both the input to the list and a compact serialization of its current view. It can be shared, bookmarked and restored by browser history without a second persistence system.

## A complete URL-state hook

The hook below reads the current parameters with `useSearchParams`, preserves the current route with `usePathname` and writes changes through the [native History API](https://nextjs.org/docs/app/getting-started/linking-and-navigating#native-history-api). Next.js keeps both navigation hooks synchronized with those native calls.

```tsx title="use-url-list-state.ts"
'use client'

import { useCallback, useMemo } from 'react'
import { usePathname, useSearchParams } from 'next/navigation'

export type ListItem = {
  id: string
  title: string
  category: string
  publishedAt: string
  // My implementation reads this value from a shared client cache. Keeping it on
  // each item makes the standalone example independent of a particular data layer.
  views: number
}

export type SortOrder = 'date-desc' | 'date-asc' | 'views-desc' | 'views-asc'

const DEFAULT_CATEGORY = 'all'
const DEFAULT_SORT: SortOrder = 'date-desc'
const SORT_ORDERS = new Set<SortOrder>([
  'date-desc',
  'date-asc',
  'views-desc',
  'views-asc',
])

export function useUrlListState(items: ListItem[]) {
  const pathname = usePathname()
  const searchParams = useSearchParams()

  const categories = useMemo(() => new Set(items.map((item) => item.category)), [items])
  const requestedCategory = searchParams.get('category')
  const category =
    requestedCategory && categories.has(requestedCategory) ? requestedCategory : DEFAULT_CATEGORY
  const searchQuery = searchParams.get('q') ?? ''
  const requestedSort = searchParams.get('sort') as SortOrder | null
  const sortBy = requestedSort && SORT_ORDERS.has(requestedSort) ? requestedSort : DEFAULT_SORT

  const updateParams = useCallback(
    (updates: Record<string, string | null>) => {
      const next = new URLSearchParams(searchParams.toString())

      for (const [key, value] of Object.entries(updates)) {
        const isDefault =
          (key === 'category' && value === DEFAULT_CATEGORY) ||
          (key === 'sort' && value === DEFAULT_SORT)

        if (!value || isDefault) next.delete(key)
        else next.set(key, value)
      }

      const query = next.toString()
      window.history.replaceState(null, '', query ? `${pathname}?${query}` : pathname)
    },
    [pathname, searchParams],
  )

  const visibleItems = useMemo(() => {
    const normalizedQuery = searchQuery.trim().toLocaleLowerCase()
    const result = items.filter((item) => {
      const matchesCategory = category === DEFAULT_CATEGORY || item.category === category
      const matchesSearch = !normalizedQuery || item.title.toLocaleLowerCase().includes(normalizedQuery)
      return matchesCategory && matchesSearch
    })

    return result.toSorted((a, b) => {
      if (sortBy === 'views-desc') return b.views - a.views
      if (sortBy === 'views-asc') return a.views - b.views

      const aTimestamp = Date.parse(a.publishedAt)
      const bTimestamp = Date.parse(b.publishedAt)
      const difference =
        (Number.isNaN(bTimestamp) ? 0 : bTimestamp) -
        (Number.isNaN(aTimestamp) ? 0 : aTimestamp)
      return sortBy === 'date-asc' ? -difference : difference
    })
  }, [category, items, searchQuery, sortBy])

  return {
    category,
    searchQuery,
    sortBy,
    visibleItems,
    setCategory: (value: string) => updateParams({ category: value }),
    setSearchQuery: (value: string) => updateParams({ q: value || null }),
    setSortBy: (value: SortOrder) => updateParams({ sort: value }),
  }
}
```

Starting from `searchParams.toString()` preserves parameters owned by other features. Default values are removed rather than written as noise, so the default view stays `/projects` instead of `/projects?category=all&sort=date-desc`.

`replaceState` is intentional here. Typing each character into a search box should not add a browser-history entry. Replacing the current entry also avoids a route transition and keeps the viewport in place. If each filter choice represents a meaningful navigation step, use `pushState` or `router.push` instead.

The hook validates the sort parameter before using it. URLs are user input too, so an unexpected value should fall back to a known default rather than entering the sorting logic.

## Connect controls to the same source

There is no parallel `useState` copy to synchronize. The selected category, input value and sort order all come from the same parameters another reader receives when opening the link.

```tsx title="project-list.tsx"
'use client'

import { type ListItem, type SortOrder, useUrlListState } from './use-url-list-state'

export function ProjectList({ projects }: { projects: ListItem[] }) {
  const state = useUrlListState(projects)

  return (
    <section>
      <label>
        Search
        <input
          type="search"
          value={state.searchQuery}
          onChange={(event) => state.setSearchQuery(event.target.value)}
        />
      </label>

      <select value={state.category} onChange={(event) => state.setCategory(event.target.value)}>
        <option value="all">All categories</option>
        <option value="web">Web</option>
        <option value="mobile">Mobile</option>
      </select>

      <select
        value={state.sortBy}
        onChange={(event) => state.setSortBy(event.target.value as SortOrder)}
      >
        <option value="date-desc">Newest</option>
        <option value="date-asc">Oldest</option>
        <option value="views-desc">Most viewed</option>
        <option value="views-asc">Least viewed</option>
      </select>

      <ul>
        {state.visibleItems.map((project) => (
          <li key={project.id}>{project.title}</li>
        ))}
      </ul>
    </section>
  )
}
```

`toSorted()` returns a new array, so the input collection is never mutated. If older browsers are part of the support target, use `[...items].sort(...)` for the same result. Memoization is a performance detail, not a second source of state.

<Callout type="success" title="What the URL now preserves">
  * A shared link opens the same search, category and order. * Refreshing reconstructs the view from
  the address. * Returning from a detail route restores the listing URL. * Filter changes do not
  remount the route or reset scroll position.
</Callout>

Not every UI choice belongs in the address bar. Hover state, open tooltips and temporary form input usually do not. A useful test is whether another person opening the URL should see the same view. If the answer is yes, keeping that state only inside React leaves out part of the page's identity.
