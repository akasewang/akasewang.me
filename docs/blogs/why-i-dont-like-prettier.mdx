excerpt: An honest, developer to developer critique of the industry's default code formatter and why rigid automation sometimes hurts semantic readability, increases pull request noise and degrades developer experience.

---

Prettier solved a real problem. It gave JavaScript teams one dependable answer to arguments about indentation, semicolons and trailing commas, then made that answer easy to run in an editor or CI job.

I still avoid it in my own projects. This is not because automated formatting is bad; I format on every commit. My objection is narrower: Prettier deliberately discards most of the layout written by the author, and some code becomes harder to read when that layout carried useful information.

## Uniform output can erase useful structure

Prettier parses a file and prints the resulting syntax tree according to its own rules. That produces consistent output, but it cannot know why an author aligned a configuration table or grouped related values.

  <Tab title="Semantic Layout">
    Alignment makes the coordinates and anchors easy to scan as columns:

    ```ts title="semantic-alignments.ts"
    export const VIEWPORT_ALIGNMENTS = {
      top:    { x: 0.5, y: 0.0, anchor: 'center-top'    },
      center: { x: 0.5, y: 0.5, anchor: 'center'        },
      bottom: { x: 0.5, y: 1.0, anchor: 'center-bottom' },
    }
    ```
  </Tab>
  <Tab title="Prettier's Output">
    The same object becomes a regular block:

    ```ts title="formatted-alignments.ts"
    export const VIEWPORT_ALIGNMENTS = {
      top: { x: 0.5, y: 0.0, anchor: "center-top" },
      center: { x: 0.5, y: 0.5, anchor: "center" },
      bottom: { x: 0.5, y: 1.0, anchor: "center-bottom" },
    };
    ```
  </Tab>
</Tabs>

The second version is not objectively wrong. For ordinary application code, its predictability is often more valuable than manual alignment. In tables, matrices and state maps, however, the first version exposes relationships that syntax alone does not.

Recent Prettier versions do preserve a multiline object when there is a newline before its first property. That heuristic helps with compact-versus-expanded layout, but it does not retain column alignment or most spacing used to express relationships within the object.

Prettier offers `// prettier-ignore` for such cases, but that comment excludes the entire following syntax node. The formatter no longer fixes indentation, spacing or punctuation inside the ignored block. I would rather preserve an intentional multiline shape while still normalizing the details around it.

```ts title="matrix.ts"
// prettier-ignore
export const matrix = [
  [1, 0, 0],
  [0, 1, 0],
  [0, 0, 1],
]
```

## `printWidth` creates noisy diffs

Prettier describes [`printWidth`](https://prettier.io/docs/options#print-width) as a target rather than a hard maximum, but crossing that target can still cause a structure to choose a different layout. A small edit may turn a compact constructor call into several lines:

<Tabs items={["Compact Call", "Expanded Call"]}>
  <Tab title="Compact Call">

    ```ts title="compact-search-params.ts"
    export const params = new URLSearchParams({ includeProfile: 'true', active: 'false' })
    ```
  </Tab>
  <Tab title="Expanded Call">

    ```ts title="expanded-search-params.ts"
    export const params = new URLSearchParams({
      includeProfile: 'true',
      active: 'false',
      verbose: 'true',
    })
    ```
  </Tab>
</Tabs>

The expanded form may be clearer, especially as the options grow. The cost appears in diffs: adding one property can replace the original line and introduce several new ones. Rename a symbol or change a type upstream and more unrelated lines may move. Reviewers then have to separate the semantic edit from formatter churn.

This is not a reason to preserve every hand-wrapped line forever. It is a reason to prefer formatters that use existing line breaks as an input when the author has already chosen a readable shape.

## Formatting should not complicate linting

ESLint and Prettier have different purposes. ESLint analyzes code for problems; Prettier prints code. Friction starts when stylistic ESLint rules disagree with Prettier's output.

A common setup has included several moving parts:

1. `eslint` for analysis
2. `prettier` for formatting
3. `eslint-config-prettier` to disable conflicting lint rules
4. sometimes `eslint-plugin-prettier` to report formatting differences through ESLint

Running Prettier as an ESLint rule is no longer the only or recommended way to combine them, but repositories still inherit that arrangement. It makes failures less clear and asks two tools to parse the same files during one lint command.

```text
  [ Source File ]
       |       |
       v       v
  [ ESLint ] [ Prettier ]
       |       |
       +--- CI + editor integrations
```

A separate `format` command avoids much of this problem. A unified tool avoids it altogether.

## What I use instead

My current preference is [Biome](https://biomejs.dev). It provides formatting, linting and import organization through one fast binary. The formatter is still opinionated, and it does not preserve every layout I write, but the combined setup is smaller and easier to keep consistent across the command line, editor and commit hooks.

Projects that need ESLint's plugin ecosystem can keep ESLint and use [ESLint Stylistic](https://eslint.style) for configurable style rules. That approach offers more control, although a large rule set also means the team owns more configuration and must decide which rules are worth enforcing.

Neither option is universally better than Prettier. A large team may reasonably choose Prettier because eliminating formatting decisions is more valuable than preserving occasional semantic alignment. Generated code and broad open-source projects also benefit from a formatter contributors already know.

For my projects, the balance falls elsewhere. I want automation to clean routine syntax without treating every author-selected line break as disposable. Consistency matters, but it is a means to readable code, not a substitute for it.
