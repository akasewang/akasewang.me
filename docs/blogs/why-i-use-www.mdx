This site uses `www.akasewang.me` as its canonical URL. The shorter apex domain still works, but it redirects here.

An apex URL looks cleaner, and modern hosting platforms make it easy to use one. I chose `www` because it gives the website its own DNS name and leaves the apex free to manage the domain as a whole. That distinction is small on a personal site, but useful once the same domain also serves APIs, assets, email and verification records.

## Cookie scope

Cookies do not automatically spread from an apex domain to every subdomain. Under [RFC 6265](https://www.rfc-editor.org/rfc/rfc6265), a cookie without a `Domain` attribute is host-only, so a cookie set by `akasewang.me` stays on that host. The broad scope appears when an application deliberately sets `Domain=akasewang.me`.

The practical benefit of `www` is that the narrow choice is obvious. Application cookies can be host-only or explicitly scoped to `www.akasewang.me`, while `api.akasewang.me` and `cdn.akasewang.me` remain outside that scope.

<Tabs items={["Broad Domain Cookie", "Host-specific Cookie"]}>
  <Tab title="Broad Domain Cookie">
    This cookie is available to `akasewang.me` and its subdomains:

    ```http
    Set-Cookie: session_id=xyz123; Domain=akasewang.me; Path=/; HttpOnly; Secure
    ```
  </Tab>
  <Tab title="Host-specific Cookie">
    This cookie is scoped to the website host:

    ```http
    Set-Cookie: session_id=xyz123; Domain=www.akasewang.me; Path=/; HttpOnly; Secure
    ```
  </Tab>
</Tabs>

Omitting `Domain` from the second example would be stricter still because it would create a host-only cookie. Either form prevents website cookies from accompanying requests to unrelated subdomains. That matters for three reasons:

- Cookies add request bytes, which is pointless overhead on asset hosts.
- Sending credentials to more hosts increases the number of systems that must be trusted and secured.
- Some CDN configurations treat requests with cookies as personalized and avoid serving a shared cached response.

`www` does not create safe cookie policy by itself; the cookie attributes still have to be correct. It does give the web application a natural boundary to enforce.

## DNS portability

The stronger reason is DNS. A `CNAME` record aliases one hostname to another, but [RFC 1034](https://www.rfc-editor.org/rfc/rfc1034) does not allow that record to coexist with other data at the same name. The zone apex already needs records such as `SOA` and `NS`, so a conventional `CNAME` cannot live there.

<Tabs items={["Invalid Apex Config", "Valid WWW Config"]}>
  <Tab title="Invalid Apex Config">
    The apex cannot be both a `CNAME` and the owner of the zone's other records:

    ```text
    @   IN  SOA   ns1.provider.com. admin.provider.com.
    @   IN  MX    10 mail.provider.com.
    @   IN  CNAME loadbalancer.cloudprovider.com.  ; conflicts with other apex records
    ```
  </Tab>
  <Tab title="Valid WWW Config">
    A subdomain has no such conflict:

    ```text
    @   IN  SOA   ns1.provider.com. admin.provider.com.
    @   IN  MX    10 mail.provider.com.
    www IN  CNAME loadbalancer.cloudprovider.com.
    ```
  </Tab>
</Tabs>

A `www` record can therefore point at a load balancer or hosting provider without copying its current IP addresses into the zone. The provider can change those addresses while the alias stays the same.

<Callout type="info" title="Apex aliases are widely available">
  Providers including Cloudflare and Vercel offer CNAME flattening, `ALIAS` records or equivalent
  apex-domain support. Those solutions are practical and remove most of the inconvenience. They are
  provider-specific extensions, though, whereas a `www` CNAME uses ordinary DNS behavior and is easy
  to move between providers.
</Callout>

## Origins and service boundaries

Putting the website on `www` and an API on `api` creates separate browser origins. CORS rules then decide which cross-origin requests the browser may expose to frontend code.

The same separation is possible with an apex website and an `api` subdomain, so this is not a unique capability of `www`. What `www` changes is the naming model: the apex represents the domain, and the website, API and asset service are peers beneath it.

That model also makes configuration easier to reason about. Email routing and ownership records stay at `akasewang.me`; web deployment settings belong to `www.akasewang.me`; API policy belongs to `api.akasewang.me`. None of this is required for a small site, but it avoids treating the website as if it were the domain's only possible service.

The choice is therefore less dramatic than it is sometimes presented. Apex domains are safe and capable when their DNS and cookie settings are configured well. I use `www` because the portable CNAME and explicit service boundary are worth more to me than removing four characters from the address bar.
